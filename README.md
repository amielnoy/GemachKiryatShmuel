# גמ"ח מזון — ניהול חלוקה שבועית

אפליקציית React + TypeScript לניהול חלוקת חבילות מזון שבועית, בנויה ל-Vercel.

- **רכז** — מנהל משפחות, מובילים ושיבוץ, ורואה את התמונה המלאה.
- **מוביל** — נכנס, בוחר את שמו פעם אחת, ורואה מסך אחד עם 2–4 המשפחות שלו. נגיעה בשורה מסמנת "נמסר".
- עובד בדפדפן במחשב, באנדרואיד וב-iOS, וניתן להתקנה למסך הבית (PWA).

---

## הפעלה מקומית

```bash
npm install
npm run dev
```

האפליקציה תעלה על `http://localhost:5173`. בלי משתני סביבה היא עובדת מיד, אבל **הנתונים נשמרים בדפדפן של המכשיר בלבד** ולא משותפים — זה מספיק כדי להתרשם, לא כדי להפעיל גמ"ח.

## שלב 1 — בסיס נתונים משותף (Supabase)

בלי זה, כל מתנדב יראה רק את מה שהוא עצמו הזין. עם זה, סימון של מוביל מופיע אצל הרכז תוך שנייה.

1. פתחו חשבון ב-[supabase.com](https://supabase.com) וצרו פרויקט חדש (השכבה החינמית מספיקה בקלות).
2. בפרויקט: **SQL Editor** → **New query** → הדביקו את כל התוכן של `supabase/schema.sql` → **Run**.
   הקובץ בטוח להרצה חוזרת, והוא גם מעביר אוטומטית נתונים שנשמרו בגרסה הקודמת (טבלת `weeks`).
   רוצים לראות את האפליקציה מלאה לפני שמזינים נתונים אמיתיים? הריצו גם את `supabase/seed.sql` —
   10 מתנדבים, 10 משפחות ושבעה ימי חלוקה אחורה. (בלי Supabase: תפריט `…` → **טעינת נתוני הדגמה**.)
3. **Project Settings** → **API**, והעתיקו שני ערכים:
   - `Project URL`
   - `anon` `public` key

## שלב 2 — פריסה ל-Vercel

הפריסה רצה **רק מתוך GitHub Actions**, ורק אחרי שבדיקת הטיפוסים, הבדיקות והבנייה עברו.
דחיפה ל-git לא מפעילה בנייה בוורסל בעצמה (`"git": { "deploymentEnabled": false }` ב-`vercel.json`) —
כך אין בנייה כפולה, וקומיט שהבדיקות שלו נכשלו לא מגיע לאוויר.

| מה קורה | התוצאה |
|---|---|
| Pull Request | פריסת תצוגה מקדימה + תגובה ב-PR עם הקישור |
| דחיפה ל-`main` | פריסה לייצור |
| הבדיקות נכשלו | אין פריסה בכלל |

### הגדרה חד־פעמית

**1. חיבור הפרויקט לוורסל** — יוצר `.vercel/project.json` מקומי (לא נכנס ל-git):

```bash
npm i -g vercel
vercel login
vercel link
```

**2. משתני סביבה — בוורסל, לא ב-GitHub.** הבנייה ב-CI שולפת אותם עם `vercel pull`,
ולכן הם חייבים לשבת בפרויקט בוורסל:

```bash
vercel env add VITE_SUPABASE_URL production
vercel env add VITE_SUPABASE_ANON_KEY production
vercel env add VITE_COORDINATOR_CODE production
```

כדאי להוסיף אותם גם ל-`preview`, אחרת התצוגה המקדימה תעבוד בלי בסיס נתונים משותף:

```bash
vercel env add VITE_SUPABASE_URL preview
vercel env add VITE_SUPABASE_ANON_KEY preview
```

**3. סודות ב-GitHub** — `Settings → Secrets and variables → Actions`:

| Secret | מאיפה לקחת |
|---|---|
| `VERCEL_TOKEN` | [vercel.com/account/tokens](https://vercel.com/account/tokens) |
| `VERCEL_ORG_ID` | `.vercel/project.json` → `orgId` |
| `VERCEL_PROJECT_ID` | `.vercel/project.json` → `projectId` |

### פריסה ידנית, כשצריך לעקוף את ה-CI

```bash
vercel --prod          # בנייה ופריסה לייצור
vercel rollback        # חזרה לפריסה הקודמת
```

> משתני הסביבה נקראים **בזמן הבנייה** ונצרבים לתוך קובצי ה-JS.
> אחרי שינוי ערך בוורסל צריך **פריסה מחדש** — עריכת הערך לבדה לא משנה את האתר החי.

## שלב 3 — הכנסת הנתונים

1. פתחו את הכתובת שקיבלתם. אם הגדרתם `VITE_COORDINATOR_CODE`, לחצו על סמל המנעול והזינו אותו.
2. תפריט `…` → **ייבוא מהגיליון**.
3. בגיליון ב-Google Sheets סמנו את השורות (בלי הכותרת — היא תזוהה גם אם תיכלל), העתיקו, והדביקו.

סדר העמודות זהה לגיליון הקיים: מס׳ · שם · כתובת · טלפון · טלפון II · מקור · ת.הצטרפות · ת. הסרה. משפחה עם ת. הסרה נכנסת ישר לארכיון.

4. הוסיפו את המובילים במסך **מובילים**, קבעו לכל אחד כמה חבילות הוא לוקח, ולחצו **חלק אוטומטית**.
5. שלחו את הקישור למתנדבים. כל אחד בוחר את שמו בכניסה הראשונה.

## אבטחה — מה שחשוב שתדעו

`VITE_COORDINATOR_CODE` הוא **גדר נוחות, לא אבטחה**. הקוד נארז לתוך קובץ ה-JavaScript שהדפדפן מוריד, כך שמי שיטרח להסתכל בקוד המקור של הדף ימצא אותו. הוא מונע ממתנדב למחוק בטעות את רשימת המשפחות — לא יותר מזה.

באותו אופן, מדיניות ה-RLS ב-`schema.sql` פותחת קריאה וכתיבה לכל מי שמחזיק בקישור. לגמ"ח שכונתי שבו הקישור עובר בין אנשים מוכרים זה סביר ומקובל. אם אתם מחזיקים פרטים רגישים של משפחות ורוצים הגנה אמיתית, הדרך היא Supabase Auth: להפעיל התחברות במייל, להחליף את המדיניות כך שתדרוש `auth.role() = 'authenticated'`, ולהזמין רק את המתנדבים. זו עבודה של כמה שעות.

**אל תשימו לעולם** את מפתח ה-`service_role` של Supabase במשתני `VITE_*` — הוא עוקף את כל ההרשאות והוא יגיע לדפדפן.

## מבנה הנתונים

ארבע טבלאות. השתיים הראשונות הן **המצב הנוכחי**, והשתיים האחרונות הן **התיעוד**:

| טבלה | מה היא מחזיקה |
|---|---|
| `families` | המשפחות: פרטי קשר, מקור ההפניה, מספר נפשות, והמוביל המשובץ **כרגע** |
| `drivers` | המתנדבים המובילים: טלפון, אזור, כמה חבילות הם לוקחים בשבוע |
| `delivery_days` | יום חלוקה אחד. המזהה הוא התאריך עצמו, למשל `2026-09-22` |
| `deliveries` | שורה אחת לכל משפחה בכל יום חלוקה: מי הוביל, מי קיבל, מה קרה |

ההפרדה הזו היא כל העניין. בגרסה הקודמת כל שבוע היה אובייקט `jsonb` יחיד שידע רק
*אילו* משפחות קיבלו חבילה — מי הביא אותה נגזר מ-`families.driver_id`, כלומר מהשיבוץ
של היום. לכן ברגע שמוביל התחלף, כל ההיסטוריה שלו נכתבה מחדש למפרע.

היום `deliveries` מצלמת את הרגע: `driver_id`, וגם `family_name` ו-`driver_name` כטקסט.
מוביל שעזב את הגמ"ח, או משפחה שהוסרה מהרשימה, ממשיכים להופיע נכון בימים שבהם הם
באמת היו שם. מאותה סיבה אין בטבלה הזו מפתחות זרים ל-`families` ול-`drivers`: מחיקה
מהרשימה הפעילה לא אמורה למחוק היסטוריה.

בונוס: סימון מסירה חזר להיות `upsert` רגיל על שורה אחת. שני מובילים שמסמנים באותה
שנייה נוגעים בשורות שונות, ולכן פונקציית המיזוג ב-SQL שהייתה נחוצה ב-v1 כבר לא נדרשת.

לדוחות יש גם `view` בשם `delivery_log` שמחבר הכול יחד.

## מסך יום החלוקה

לשונית **יום חלוקה** היא התמונה המלאה של יום אחד: מי מחלק, למי, ומה הסטטוס.

- **היום הנוכחי** — נגיעה בשורה מסמנת "נמסר", בדיוק כמו במסך החלוקה.
- **פתיחת יום החלוקה** — שומרת את התוכנית של השבוע (שורה לכל משפחה פעילה, עם המוביל
  שלה כרגע). עד שלוחצים, הרשימה היא רק תצוגה מקדימה מחושבת. אחרי שלוחצים, היא
  ההיסטוריה של השבוע — וגם אם תשנו שיבוצים מחר, היא לא תשתנה. סימון מסירה פותח את
  היום אוטומטית, כך שאי אפשר לאבד תיעוד בגלל ששכחתם ללחוץ.
- **ימים קודמים** — נבחרים מהרשימה הנפתחת ומוצגים לקריאה בלבד.
- **הדפסה** — דף חלוקה מסודר לפי מוביל, עם תיבות סימון.
- **ייצוא** — CSV של היום. ייצוא של *כל* ההיסטוריה נמצא בתפריט `…`.

יום החלוקה הוא יום שלישי כברירת מחדל. משנים את זה בקבוע `DELIVERY_WEEKDAY`
ב-`src/lib/utils.ts` (`0` = ראשון). השינוי משפיע רק על ימים עתידיים — ימים שכבר
נרשמו שומרים את התאריך שלהם.

ולכן בדיקה אדומה עוצרת את הפריסה — ראו [שלב 2](#שלב-2--פריסה-ל-vercel).

> `npm run typecheck` הוא `tsc -b --force`, ולא `tsc --noEmit`. עם project references
> הפקודה השנייה לא בודקת שום קובץ ופשוט מצליחה תמיד.

## הערות

- **התקנה לנייד**: באנדרואיד Chrome יציע "הוספה למסך הבית". ב-iOS: שיתוף ← "הוספה למסך הבית".
- **מעבר בין שבועות**: יום החלוקה מתחלף אוטומטית בכל שבוע. הסימונים של השבוע שעבר לא
  "מתאפסים" — הם פשוט שייכים ליום אחר, ונשארים זמינים לצפייה ולייצוא.
